# S3: from Boto3 to the browser, least privilege, and the twin's wire formats

Written by boto3.aws.c@SovereignWebsite.dinis, 23 Nov 2026, first wake. Read from site/s3.js, site/twin.js, site/transport.js, site/plan.js and site/cloudformation/bootstrap.yaml at dev 4433914, and checked against AWS's public documentation (sources at the end). No AWS endpoint was called.

## 1. What a Boto3 user does, and what the page does instead

| Typical Boto3 call | Wire call | In the page today | IAM action |
|---|---|---|---|
| `s3.list_buckets()` | `GET /` on s3.amazonaws.com | Not usable from a page (s3.js design note: ListBuckets does not answer web pages). The page lists buckets through Cloud Control `ListResources` for `AWS::S3::Bucket` instead. | `cloudformation:ListResources` (Cloud Control actions use the `cloudformation:` prefix [3]) plus the S3 list handler's own permissions (to verify, section 4) |
| `s3.get_bucket_location()` / `head_bucket()` | `GET /?location` / `HEAD /` | Cloud Control `GetResource`, reading `RegionalDomainName` to get the region | `cloudformation:GetResource` plus the read handler's permissions |
| `paginator('list_objects_v2')` with `Delimiter='/'` | `GET /?list-type=2&delimiter=/&prefix=...&continuation-token=...` | Same call, signed with SigV4 in the page, 500 keys a page, "Load more" by `NextContinuationToken` | `s3:ListBucket` on the bucket ARN |
| `s3.get_object(Bucket, Key)` | `GET /key` | Same call | `s3:GetObject` on `arn:aws:s3:::bucket/*` |
| `s3.get_object(..., Range='bytes=a-b')` | `GET /key` with `Range` | Same call, used by zip.js to read inside zips | `s3:GetObject` |
| `s3.head_object()` | `HEAD /key` | Not used yet (s3.aws.c's note item 1 wants it before large downloads) | `s3:GetObject` |
| `get_bucket_cors()` / `put_bucket_cors()` | `GET/PUT /?cors` | Read through Cloud Control `GetResource`; written as a plan through Cloud Control `UpdateResource` | read: handler permissions; write: `cloudformation:UpdateResource` plus `s3:PutBucketCORS` |

The browser can do one thing Boto3 users rarely do: read a byte range inside a zip or gzip in place, without downloading the object.

## 2. Least privilege for the S3 browser

Today (bootstrap.yaml): the read role has `s3:Get*` and `s3:List*` on `*`; the change role adds `s3:PutBucketCORS` and the Cloud Control write actions on `*`.

What the S3 browser actually calls is far less. A proposal for iam.aws.c and aws.c to weigh (not a plan, nothing here changes AWS):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ListTheBuckets", "Effect": "Allow",
      "Action": ["cloudformation:ListResources", "cloudformation:GetResource"], "Resource": "*" },
    { "Sid": "ListInsideBuckets", "Effect": "Allow",
      "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::*" },
    { "Sid": "ReadObjects", "Effect": "Allow",
      "Action": "s3:GetObject", "Resource": "arn:aws:s3:::*/*" }
  ]
}
```

Plus whatever the `AWS::S3::Bucket` list and read handlers need (section 4). Notes:

- `s3:Get*` also grants reading every bucket's policy, ACL, replication, lifecycle and more. The browser reads none of these directly. Narrowing to `s3:GetObject` and `s3:ListBucket` removes them unless the Cloud Control read handler needs them, which is the open question in section 4.
- Cloud Control does not support resource-level permissions or service condition keys [3], so `Resource: "*"` stays for those two actions. The S3 actions can be scoped to named buckets once Dinis says which buckets the hub may see.
- `s3:ListBucket` decides 404 versus 403: without it, GetObject on a missing key returns 403 Access Denied, with it 404 Not Found [2]. The page should read 403 on an open as "missing or not allowed", not as "not allowed".

## 3. The twin's S3 wire formats against AWS

Checked against the ListObjectsV2 [1] and GetObject [2] references. Ranked by what would break or mislead when the page meets real S3.

| # | Twin today | AWS | Effect | Severity |
|---|---|---|---|---|
| Q1 | ListObjectsV2 never paginates: no `IsTruncated`, no `NextContinuationToken`, `max-keys` ignored | Up to 1,000 keys (or `max-keys`); `IsTruncated` always returned; `NextContinuationToken` when truncated; `ContinuationToken` echoed | "Load more" in s3.js is never exercised by the twin or its tests. A wrong token round trip would ship unseen. | High |
| Q2 | Range only for `bytes=a-b`; `bytes=a-` and `bytes=-n` fall through to a 200 with the whole object; a start past the end gives an empty 206 | Single ranges per RFC 9110, including open and suffix forms; multiple ranges not supported [2]; a range past the end should be refused under RFC 9110 (S3's exact error code to confirm from the error reference) | A reader that asks for the last n bytes (a zip's tail) would work in the twin by accident and differ live. | High |
| Q3 | 206 carries only `content-type` | 206 carries `Content-Range: bytes a-b/total`, `Accept-Ranges: bytes`, `ETag`, `Last-Modified` [2] | Code that learns the size from `Content-Range` cannot be tested. Also, live, the page can read `Content-Range` only if the bucket's CORS rule exposes it: plan.js exposes `ETag, Content-Type, Content-Length, Last-Modified`, not `Content-Range`. | Medium |
| Q4 | `<Contents>` has `Key`, `Size`, `LastModified` only | Also `ETag` and `StorageClass` [1] | Nothing breaks today; cache keys or "GLACIER, cannot open" hints cannot be tested. | Medium |
| Q5 | `<ListBucketResult>` without the namespace, and without `KeyCount`, `MaxKeys`, `Delimiter` | `xmlns="http://s3.amazonaws.com/doc/2006-03-01/"`, `KeyCount`, `MaxKeys`, `Delimiter`, `IsTruncated` [1] | s3.js uses `getElementsByTagName`, which ignores the namespace, so it works; a namespace-aware reader (`getElementsByTagNameNS`, XPath) would pass in the twin and fail live. | Low |
| Q6 | Missing bucket is answered `NoSuchBucket` 404 before the CORS check | A bucket that does not exist has no CORS rule for this origin, so the page sees a network failure, not the XML | The twin shows a clearer error than AWS can; the page's live message for this case is untested. | Low |
| Q7 | Region in the host is ignored for S3 | A request to the wrong regional endpoint is refused (exact code to confirm from S3's error reference) | The region logic in s3.js (from `RegionalDomainName`) is never tested against a wrong region. The twin already does this for Cloud Control `UpdateResource`. | Low |
| Q8 | HEAD is answered with a body, as GET | HEAD returns headers only | Matters once HEAD is used (s3.aws.c item 1). | Low |
| Q9 | Error bodies have `Code` and `Message` only | Also `RequestId` and `HostId`, and `Key` / `BucketName` where relevant | Cosmetic. | Low |

Not a quirk, and good: the twin rejects an S3 read on a bucket without a CORS rule with a `TypeError("Failed to fetch")`, which is what a browser sees. Path-style for dotted names and virtual-hosted otherwise match AWS [2].

To check next, not assumed: whether Firehose-written `.gz` objects carry `Content-Encoding: gzip`. If they do, `fetch` decompresses them before the page sees the bytes, and a byte range is a range of the compressed object. s3.aws.c's note says the page copes with the whole-object case; the twin seeds them without `Content-Encoding`, so the other case is untested.
