# 08: vaults.aws.a's deploy design (04) against AWS's documentation

Sources and method: input is design 04 (vaults.aws.a, work/vaults.aws.a, 8b1d336). Every *check* was compared with AWS's public documentation only (docs.aws.amazon.com), fetched with curl on 23 Nov 2026. No AWS API was called and no credential was used or asked for. Where a page does not say a thing in so many words, the verdict is "To confirm" or "Partly", never assumed. Drafted with a Sonnet sub-agent; boto3.aws.a re-read the deciding quotes (OAC needs AWS_IAM and x-amz-content-sha256; new Function URLs need both permissions; quick-create templateURL in S3; ECR in the same region; no pull-through cache for Lambda).

## Verdicts

| 2 | One stack creates resources in one region, so the cert is a separate stack | Partly | The pages read do not state "one stack, one region" as a sentence. The two-stack design is sound; the exact wording is to confirm. |
| 3 | A Lambda Function URL takes no custom domain, so CloudFront sits in front | To confirm | The docs say a function URL is a generated endpoint, `https://<url-id>.lambda-url.<region>.on.aws`, that "never changes". They do not say a custom domain is impossible. The design's conclusion (CloudFront in front for the domain) stays valid. |
| 4 | `GenerateSecretString` generates the token, never typed or shown | Partly | Confirmed that it generates a password. Options: `PasswordLength` (default 32), `ExcludeCharacters`, `ExcludePunctuation`, `ExcludeUppercase/Lowercase/Numbers`, `IncludeSpace`, `RequireEachIncludedType`, `SecretStringTemplate` with `GenerateStringKey`. `Ref` returns the secret's ARN, not the value. ## Notes

**A. OAC (item 9, design 2 and 6.2).** The OAC page (CloudFront guide) says: the distribution must have the function URL as origin; "you must specify AWS_IAM as the value for the AuthType parameter"; grant `cloudfront.amazonaws.com` the action `lambda:InvokeFunctionUrl` (and `lambda:InvokeFunction` in the example) with `--source-arn` set to the distribution's ARN; create an OAC of origin type Lambda with signing behaviour "always". Caveat, marked Important: for PUT or POST, "your users must compute the SHA256 of the body and include the payload hash ... in the x-amz-content-sha256 header when sending the request to CloudFront. Lambda doesn't support unsigned payloads." sgit and the vault UI push with POST/PUT and are not shown to send that header, so OAC is likely to break writes unless the clients change. Design 2 rejects IAM auth because it "breaks sgit and browser clients"; with OAC the clients no longer sign, but they hit this header rule instead. Keep v1 on `NONE` plus the server token, as drafted, and treat OAC as blocked until the clients are tested. The page also mentions a separate OAC page for a "Lambda Web Function" origin; I could not read it (empty fetch), so whether it applies to a web-adapter function is **To confirm**.

**B. ACM and DNS elsewhere (item 5, design 2 outputs).** (1) The `DomainValidationOption.HostedZoneId` must be the bare ID (`Z111...`, not `/hostedzone/Z111...`), and the page says it is "required for publicly trusted certificates", which sits oddly beside the "DNS elsewhere" case. How to write a template that works for both paths is **To confirm**. (2) The certificate's attributes are only `Ref` (ARN) and `CertificateArn`/`CertificateStatus`: there is no attribute for the validation CNAME. So design 2's `DnsRecords` output cannot carry the validation record, and stack outputs appear only once creation completes, which for DNS elsewhere is after the CNAME exists. The customer must read the CNAME from the ACM console (certificate in us-east-1) while the stack waits.

**C. Quick-create link (item 7).** Format as in the design: `https://<region>.console.aws.amazon.com/cloudformation/home?region=<r>#/stacks/create/review?templateURL=<S3 URL>&stackName=<name>&param_<Name>=<value>`. Template URL: "located in an Amazon S3 bucket" (formats `https://s3.<region>.amazonaws.com/<bucket>/<key>` or `https://<bucket>.s3.<region>.amazonaws.com/<key>`); URL-encode it. Stack name: letters, digits, hyphens, starts with a letter, at most 128 characters (`sws-vault-<id>` fits). `param_` names are case sensitive and must match the template; unknown ones are ignored, and `NoEcho` parameters are ignored. The design's "one immutable URL per version" is fine only if each template sits in an S3 bucket (per region, since the URL is regional in form). Capabilities: the console asks the customer to tick "I acknowledge that this template may create IAM resources"; the quick-create page shows no link parameter for it. Whether named IAM roles need the stronger named-IAM acknowledgement is **To confirm** (page not read).

**D. Cross-region options (item 2).** StackSets (create, update or delete stacks across accounts and Regions in one operation, admin account plus target accounts) is the AWS route for multi-region; it needs StackSets permissions set up in the customer's account, so it does not fit a one-click link. `Fn::GetStackOutput` can read an output from a stack in another Region or account without an export, a weak reference resolved at create or update: useful for the vault stack to read the edge stack's certificate ARN instead of the customer pasting it (not tested; the design's "update with the ARN" still works).

**E. Other points against the design.** (1) Lambda: the Function URL page notes that from October 2025 new function URLs need both `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` in the resource policy, so the `NONE` public permission needs both statements (iam.aws.a, step 3). (2) ECR: creating a function from an image needs repository-policy permissions on the deploy role (the page lists `GetRepositoryPolicy`, `SetRepositoryPolicy`, `BatchGetImage` and related); cross-account pulls need the repository policy in the owner's account as well. Question 4(b) therefore works in principle: one ECR repository per region, filled by cross-Region replication, repository policy allowing Lambda to pull. Pull-through cache does not help. (3) CloudFront Function code is 10 KB at most and cannot read request bodies; the `/health` JSON is far within that. (4) CloudFront keeps the viewer certificate rule (us-east-1) even if the origin is in another region: unaffected.

## What changes for vaults.aws.a / cloudformation.aws.a

- Keep the `us-east-1` edge stack for the certificate; word the reason as "CloudFront needs the ACM certificate in us-east-1" (confirmed) and "a stack lives in one region" (to confirm, but the design holds either way).
- Do not put the certificate's validation CNAME in the `vault` stack's `DnsRecords` output: CloudFormation exposes no such attribute. Tell the customer to read it from the ACM console in us-east-1 while the edge stack waits in CREATE_IN_PROGRESS (no timeout is documented, so the page should say how long it will wait).
- Use the bare hosted zone ID (no `/hostedzone/` prefix) in `DomainValidationOptions`; settle with boto3.aws.a how to build the "DNS elsewhere" variant given that `HostedZoneId` is documented as required for public certificates.
- Publish each template version to an S3 bucket: the quick-create `templateURL` must be an S3 URL, not any HTTPS address. Leave capabilities to the customer's tick in the console and mark IAM resources clearly in the template description.
- Generate the token with `GenerateSecretString`: set `PasswordLength` explicitly (default 32), `ExcludePunctuation: true` (or `ExcludeCharacters`) so it is safe in a header, and expose only the ARN in outputs. Remember the dynamic reference puts the value in the function's configuration (design 6.1 already says so).
- Keep Function URL auth `NONE` in v1. OAC needs `AWS_IAM` and a client-computed `x-amz-content-sha256` on POST/PUT, which sgit is not shown to send: treat OAC as a hardening step blocked on a client test. Grant both `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` in the function's resource policy.
- `/health` as a CloudFront Function on viewer request is fine: inline `FunctionCode`, runtime `cloudfront-js-2.0`, code under 10 KB, no request body access. Test the `Fn::Sub` substitution in cfn-lint before relying on it.
- Image source (question 4): ECR in the function's region is mandatory. Option (b) is possible (cross-account pull needs repository policy plus identity permission, same region), with one repository per region filled by ECR cross-Region replication. Pull-through cache cannot be used with Lambda. Give iam.aws.a the ECR actions for the function and deploy roles.
- Consider `Fn::GetStackOutput` so the `vault` stack reads the certificate ARN from the edge stack, instead of an update with a pasted ARN. Not tested.

## Addendum, 16:30 UTC: can a quick-create link carry the service role (RoleARN)?

Asked by ux.aws.a for design 06 option (b), relayed by conductor.aws.a. **No, as documented.** The quick-create page says "CloudFormation supports the following URL query parameters" and lists three only: `templateURL` (required, S3), `stackName` and `param_<Name>`. The service role is a stack option the customer chooses on the Quick create stack page itself ("Permissions: Choose the IAM service role for stack operations"), alongside tags, failure options and capabilities. Any other query parameter is undocumented: not to be relied on, and not tried here (no console session, by rule).

A template cannot name its own service role either: `RoleARN` is a parameter of the CreateStack call, not of the template, and once given it stays with the stack for every later operation; whoever passes it needs `iam:PassRole` (CloudFormation User Guide, service role page).

So the options for design 06 are: (a) no service role, the customer's own console identity runs the `vault` stack: one link, one click, plus the IAM acknowledgement; (b) one link, and the page tells the customer to pick `sws-vault-<id>-deploy` under Permissions: one extra choice, easy to miss, and the stack then runs with that role for its life; (c) two stacks as drafted. Recommendation from the AWS side: (a) for v1 if security.aws.a accepts that the customer's own session creates the resources, since it is the one-link path; (b) if the deploy role is a requirement.
