## Addendum, 18:10 UTC: sns:Protocol on Subscribe

Confirmed. The SNS SAR lists `sns:Endpoint` and `sns:Protocol` as condition keys of `sns:Subscribe`; `sns:Protocol` "Filters access by the protocol value from a Subscribe request or a previously confirmed subscription", type String. So `StringEquals sns:Protocol = email` limits a role to email subscriptions; `sns:Endpoint` ("the URL, email address, or ARN from a Subscribe request") can pin the address too. Protocol values are lowercase in the Subscribe API (`email`, `email-json`, ...); `email-json` is a different protocol and is excluded by an exact match. Source: https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonsns.html, read 23 Nov 2026.

## Addendum, 18:15 UTC: the AlarmActions gap, followed up (for security.aws.a)

1. **Other keys.** The CloudWatch SAR's condition keys are `cloudwatch:AlarmActions`, `cloudwatch:AlarmTagsPropagationEnabled`, `cloudwatch:namespace`, `cloudwatch:requestInsightRuleLogGroups`, `cloudwatch:requestManagedResourceARNs` and `cloudwatch:ResourceArn`. None names OKActions or InsufficientDataActions, and `cloudwatch:namespace` is listed for PutMetricData, not PutMetricAlarm; there is no MetricName key. So whether OK and insufficient-data actions are filtered by `cloudwatch:AlarmActions` stays **to confirm**, and nothing else can pin them or the metric an alarm watches.
2. **EC2 or SSM actions on an alarm.** PutMetricAlarm: "you must have Amazon EC2 permissions for some alarm operations: The iam:CreateServiceLinkedRole permission for all alarms with EC2 actions; The iam:CreateServiceLinkedRole permissions to create an alarm with Systems Manager OpsItem or response plan actions", and "The first time you create an alarm ... CloudWatch creates the necessary service-linked role for you" (AWSServiceRoleForCloudWatchEvents, AWSServiceRoleForCloudWatchAlarms_ActionSSM). The documented requirement is `iam:CreateServiceLinkedRole`, not EC2 or SSM rights. **So lacking EC2 and SSM rights does not make the deploy role safe**: if that service-linked role already exists in the customer's account, the documented requirement is already met. An alarm whose OK or insufficient-data action is `arn:aws:automate:<region>:ec2:stop` or `terminate`, watching any instance's metric, would act on that instance.

Recommendation: deny `iam:CreateServiceLinkedRole` on the deploy role (closes it only where the role does not exist yet); scope PutMetricAlarm to the Vault's own alarm names; and treat the OK/insufficient-data question as open until a test in a throwaway account shows `cloudwatch:AlarmActions` covers them. If it does not, the safe shape is that the stack creates no alarm with the deploy role and the customer's own identity makes the cost alarm. Sources: https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazoncloudwatch.html; https://docs.aws.amazon.com/AmazonCloudWatch/latest/APIReference/API_PutMetricAlarm.html (read 23 Nov 2026).

## Addendum, 24 Nov 00:25 UTC: WebACLId and wafv2 permissions, rechecked (for iam.aws.a's 07-web-acl-of-another-vault)

- The CloudFront SAR's rows: `CreateDistribution` (no resource type; keys `aws:RequestTag/${TagKey}`, `aws:TagKeys`) and `UpdateDistribution` (resource `distribution*`; key `aws:ResourceTag/${TagKey}`) list **no dependent actions**, and the page mentions `wafv2` nowhere.
- The WAF guide's "Permissions for AssociateWebACL": "For Amazon CloudFront distributions, instead of this action, use the CloudFront action UpdateDistribution", with a wafv2 permission given for every other resource type but none for CloudFront; the AssociateWebACL API says the same.
- So, as documented, attaching any WAFv2 web ACL ARN to a distribution is gated only by `cloudfront:CreateDistribution` / `cloudfront:UpdateDistribution`, and **no CloudFront condition key names the WebACLId**. A deploy role that may update its own distribution can therefore point it at another web ACL (or remove it) unless something else stops it. Whether CloudFront checks the caller for `wafv2:GetWebACL` behind the scenes is still not documented: to confirm on the first real deploy; do not rely on it as a guard.

Sources (read 24 Nov 2026): https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazoncloudfront.html; https://docs.aws.amazon.com/waf/latest/developerguide/security_iam_service-with-iam.html; https://docs.aws.amazon.com/waf/latest/APIReference/API_AssociateWebACL.html.
