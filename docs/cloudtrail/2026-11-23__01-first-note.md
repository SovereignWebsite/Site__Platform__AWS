## The goal, from a user's chair

Dinis: "finally understand what ... is happening"; open source, so anyone can drop in their own CloudTrail dump. A first-time user should, in under a minute and without reading anything:

1. see **what happened, when, and by whom**, newest first, in plain words ("the change role rewrote who may assume demo-dns-role"), not raw JSON;
2. click **any asset** (a bucket, a role, a stack) and see everything that touched it;
3. see **what deserves attention** first: changes to trust and permissions, things done from somewhere new, things that failed;
4. **drop in their own file** and get the same views, with nothing leaving the browser.

## What the twin has today

One file, in the trail bucket `aws-cloudtrail-logs-111122223333-demo`:

`AWSLogs/111122223333/CloudTrail/eu-west-2/2026/11/22/111122223333_CloudTrail_eu-west-2_20261122T1000Z_demo.json.gz`

with two records:

| Time (UTC) | Who | What | On |
|---|---|---|---|
| 10:01:02 | assumed-role/sws-aws-platform-read | s3 GetObject | demo site bucket, data/vaults.json |
| 10:04:40 | assumed-role/sws-aws-platform-change | iam UpdateAssumeRolePolicy (us-east-1) | role demo-dns-role |

What is right: the key layout and file name follow CloudTrail's S3 delivery pattern; the file is a gzip of `{"Records": [...]}`; IAM calls are recorded in us-east-1, as AWS does for global services. The S3 browser (site/s3.js) already unzips and formats it, so a user can read it today, as JSON.

## Gaps in the twin's records

1. **Too few to see anything.** Two records make no timeline, no per-asset view and no alarm. The demo packs (baseline, attack, surge) change the CloudFront logs but not the trail.
2. **Fields a real record always has are missing**: `eventVersion`, `eventID`, `eventType` (AwsApiCall, AwsConsoleSignIn, AwsServiceEvent), `recipientAccountId`, `userAgent`, `readOnly`, `managementEvent`, `eventCategory`, and `responseElements` where there is one. The second record has no `sourceIPAddress`. A view built on these two records would break on the first real file.
3. **No failures.** Real trails are full of `errorCode` / `errorMessage` (AccessDenied and the like); these are what an alarm view lives on.
4. **No sign-in or role assumption.** The story of a session starts with `AssumeRoleWithWebIdentity` (sts.amazonaws.com), which is how this hub signs in. Without it, the "by whom" has no beginning.
5. **The role name does not match the twin.** The trust policy in the twin is on `sovereignwebsite-factory-dns`; the trail says `demo-dns-role`. A user clicking from the record to the role finds nothing.
6. **The comment says "digest-style"**, but these are log records. CloudTrail digest files (`CloudTrail-Digest/`, for integrity checks) are something else and could come later as their own feature.
7. **GetObject is a data event**: it appears only if the trail logs S3 data events, which costs extra. Worth saying in the view, so a user with a real dump knows why their reads are missing.

## Proposal for the twin (for aws.c and dev.1 / dev.2, who own site/twin.js)

A synthetic trail per pack, a few hundred records over the same three days as the CloudFront logs, generated with the twin's seeded random so it is the same every time, all records with the full field set above:

- **baseline**: Dinis signs in (AssumeRoleWithWebIdentity to the read role), lists and reads buckets, Firehose writes logs (AwsServiceEvent), one CloudFormation stack update through a change set, the odd AccessDenied from a misclick.
- **attack**: the same, plus the R-008 path from docs/security/risks.md played as a story: the change role calls CreateChangeSet with a template that adds `PutRolePolicy`, then ExecuteChangeSet, then UpdateAssumeRolePolicy on the DNS role (R-005), from an address and user agent never seen before. This is exactly what R-008 (c) asks a CloudTrail alert to catch, so the twin shows the alarm firing.
- **surge**: the trail barely changes (traffic is CloudFront's, not the API's); worth showing as such, since "the site is busy but nobody changed anything" is itself an answer.

I can write the generator as a separate file for review (for example site/twin-trail.js) if aws.c gives me that path, or hand the record list over as data for dev.2 to wire in.

## The views

All three read the same normalised list of records, from the twin or from a dropped file. Five UIs as the programme asks; the first is the one to build first.

### 1. Timeline (CT-1)

- One line per event, newest first, grouped by hour, with a sentence made from the record: **who** (the role or user, short), **did what** (the API call in words: "rewrote the trust of", "read", "listed"), **to what** (the asset, a link), **from where** (address, region), and a mark for failed calls.
- Filters as chips, not a query language: read or change, failed only, by service, by who, by asset. A time brush over a small bar chart of events per hour to zoom.
- Click a line to open the raw record, formatted (the S3 browser's JSON view, reused), with the fields explained.
- An address for every state (`#from=...&to=...&who=...`), so a link shows the same view. No cookie, nothing stored but the user's own choices.

### 2. Per-asset activity

- Every asset in the twin (bucket, role, stack, distribution) gets a panel: what touched it, who, how often, last change, last failure. Fed by and feeding ontology.aws.a's graph (the asset ids should be the same ARNs).
- From the S3 browser and the IAM views, one link: "activity on this bucket" / "who used this role".

### 3. Alarms and attention (CW-1 starts here)

Rules that run in the page over the records, each written in words, each with the records that fired it:

- any change to IAM trust or permissions on `sws-aws-platform-*` or the DNS role (UpdateAssumeRolePolicy, PutRolePolicy, AttachRolePolicy, CreatePolicyVersion);
- any ExecuteChangeSet on the hub's stack (R-008 (c));
- a call from an address or user agent not seen in the earlier days;
- a burst of AccessDenied from one identity;
- CloudTrail itself changed (StopLogging, DeleteTrail, PutEventSelectors).

These are the same rules that, once Dinis approves, aws.c can plan as real EventBridge rules or CloudWatch alarms; the page shows what they would have caught on the twin first.

### 4 and 5

A map view (who connects to what over the period, from the graph) and a "story" view (one session from sign-in to sign-out as a narrative), both after the first three.

## Drop in your own CloudTrail dump

- Drag a `.json` or `.json.gz` (or several, or a zip of a downloaded `AWSLogs/` folder, read by byte ranges with zip.js) onto the page. Parsed with DecompressionStream in the browser; nothing is uploaded, nothing stored unless the user asks.
- Formats to accept: the S3 delivery format (`{"Records": [...]}`) first. Other export shapes (the console's event history download, CloudTrail Lake query results) to be checked against AWS's documentation before we claim them; I will not guess their layout.
- Large dumps: stream records, keep an index by time, asset and identity, render only what is on screen. Show counts first ("41,233 events over 9 days, 3 alarms").
- Say clearly on the page: this runs in your browser; the file never leaves your machine.

Nothing here touches AWS or needs a credential. The dropped-file feature reads untrusted JSON: render it only through textContent and DOM nodes (as s3.js does), never as HTML; cap sizes; and keep it inside the existing CSP. Left for security.aws.c to review when there is code.
