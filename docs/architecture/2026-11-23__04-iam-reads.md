# Design 04: IAM reads (IamApi, its twin answers, its graph adapter)

Written by architect.aws.a@SovereignWebsite.dinis, 23 November 2026 ~11:15 UTC. Status: **proposed**. Short, because design 03 already sets the rules every service API follows. For dev.2.aws.a to build, iam.aws.a and boto3.aws.a to challenge, aws.c to land the twin part, security.aws.a to review. Sources: design 03; `site/twin.js` on dev (its `iam()` answers only `GetRole` and `UpdateAssumeRolePolicy` for three roles); ontology.aws.a's golden graph (work/ontology.aws.a 1cb46d5), whose IAM edges are listed below.

## Scope: what the page shows about IAM, and what it does not

**In:** roles, who may assume each (the trust policy, read into principals and conditions), and which policies each has (attached managed policies and inline policy names), with each policy's document on request. That is what the Map needs to draw "who can become what" and what iam.aws.a needs to start on over-privilege.

**Out, on purpose:**
- **No policy evaluation or simulation in the page.** Deciding what a set of policies allows (with conditions, boundaries, SCPs, resource policies) is easy to get wrong and a wrong "allowed" or "denied" misleads more than no answer. If it comes, it comes as its own design, starting from `iam:SimulatePrincipalPolicy` (an AWS answer, evidence `api`), not our own evaluator.
- No users, groups or access keys **in this step**: the platform uses roles only (bootstrap.yaml). Not never: "all the right accounts" needs to know whether IAM users or keys exist from before the platform. `ListUsers`, `ListAccessKeys` and `GetAccessKeyLastUsed` return metadata only (key id, age, last used, never the secret); that is a later, separate design with iam.aws.a and security.aws.a.
- No writes: changes to IAM are plans and Approve (design 01; R-001, R-008).

## IamApi

IAM is global: `iam.amazonaws.com`, signed for us-east-1, Query protocol (form body, XML answer), paged by `Marker` / `IsTruncated` (encoded into the opaque `next`, design 03 refinement 2).

```
IamApi(send)
  .roles({ next })              -> { items: [{ name, arn, path, created, description, maxSession, trust: Trust }], next }   ListRoles
  .role(name)                   -> { name, arn, path, created, trust: Trust, lastUsed: { when, region } | null,
                                     boundary: { type, arn } | null }                                       GetRole
  .attached(name, { next })     -> { items: [{ name, arn }], next }                                       ListAttachedRolePolicies
  .inline(name, { next })       -> { items: [name], next }                                                ListRolePolicies
  .inlineDocument(name, policy) -> PolicyDocument                                                          GetRolePolicy
  .policyDocument(arn)          -> { version, document: PolicyDocument }                                   GetPolicy + GetPolicyVersion (default)
  .providers()                  -> [{ arn }]                                                               ListOpenIDConnectProviders
  .provider(arn)                -> { arn, url, clientIds, created }                                        GetOpenIDConnectProvider
```

- `Trust` is the trust policy **read, not judged**: `{ statements: [{ effect, actions, principals: [{ kind: "service" | "aws" | "federated", id }], conditions: [{ op, key, values }] }] }`. Policy documents arrive URL-encoded in IAM's XML; IamApi decodes them and parses the JSON (as the twin's `GetRole` already encodes them). Values stay as AWS wrote them; `Statement` and single values normalised to arrays only.
- **Shapes checked by boto3.aws.a** (docs/boto3/2026-11-23__06-iam-read-shapes.md, work/boto3.aws.a a83ea2f):
  - `ListRoles` already carries each role's trust policy, so `roles()` returns `trust` too and the trust graph needs no `GetRole` per role; `GetRole` is called only for `lastUsed` and `boundary`, which `ListRoles` lacks.
  - `RoleLastUsed` covers 400 days: no `LastUsedDate` means "not used in the last 400 days", never "never used". The page says exactly that.
  - `ListOpenIDConnectProviders` gives ARNs only: `providers()` derives the host from the ARN (`oidc-provider/<host>`); `provider(arn)` (`GetOpenIDConnectProvider`) is called only when the client ids are needed for an `aud` condition.
  - Every policy document, from any call, is passed through `decodeURIComponent` before `JSON.parse` (AWS's notes and samples disagree on which calls encode).
  - Paging: follow `IsTruncated`; send `Marker` only when it was true; `MaxItems` defaults to 100.
- **The permissions boundary is part of a role** (iam.aws.a): a page that shows a role's policies without its boundary overstates what the role can do, so `role()` returns it and every view shows it beside the policies.
- `path` is shown, and service-linked roles (under `/aws-service-role/`) are grouped and marked "AWS manages these", so the list does not look over-privileged when it is not.
- `x-aws-actions`: `iam:ListRoles`, `iam:GetRole`, `iam:ListAttachedRolePolicies`, `iam:ListRolePolicies`, `iam:GetRolePolicy`, `iam:GetPolicy`, `iam:GetPolicyVersion`, `iam:ListOpenIDConnectProviders`, `iam:GetOpenIDConnectProvider` (client ids, which tie a trust's `aud` condition to its provider), `Resource: "*"`. All are reads.
- **Template v3 (iam.aws.a):** under P-IAM-001 v2.4 the read role's boundary (ReadBoundary) names only today's reads, so the IAM reads in ViewOnlyAccess and SecurityAudit are capped out. v3 must add these nine actions both to the read role, as its own inline statement, and to ReadBoundary; raising a boundary is a console act, so v3 is a console apply or ships with v2.4 in one console visit. That is aws.c's plan and Dinis's Approve; nothing here calls real AWS before it.

## Twin answers (a patch for aws.c, under design 02's world when it lands)

The twin's IAM grows from three trust policies to the roles the golden graph already names: the platform's two roles and the DNS role, plus the four demo roles the Lambda and Firehose twins point at (`demo-handler-role`, `demo-log-enricher-role`, `demo-nightly-report-role`, `demo-cloudfront-logs-firehose`), each with a plausible trust (the service principal of what runs as it), and the two AWS managed policies the golden graph names (`SecurityAudit`, `job-function/ViewOnlyAccess`) attached where the stack seed says. Managed policy documents are **not** copied into the twin: AWS's own text is long and changes, so the twin answers `GetPolicyVersion` for AWS managed policies with a short placeholder document marked as such (`"Sid": "TwinPlaceholder"`) and the page says "AWS managed policy; open it in AWS's documentation" rather than show invented content. One `ListRoles` page of 2 items with `IsTruncated` exercises paging. Boundaries: once decision 6 (P-IAM-001 v2.4) is taken, the two platform roles get their boundaries in the twin, and `GetPolicyVersion` answers for the two customer boundary policies with their text from the template (ours, so no placeholder); until then the twin shows them without, as the real account is today.

## Graph adapter (`Graph.add.iam`)

The golden graph's IAM edges, and where each comes from at run time:

| Edge | Count in golden | From |
|---|---|---|
| role `in` account | 3 | `roles()` (api) |
| role `trusts` identity provider | 3 | `role(name).trust` federated principals (api) |
| role `allows_subject` GitHub subject | 2 | trust conditions on `token.actions.githubusercontent.com:sub` (api) |
| role `has_policy` policy | 2 | today from the stack (template); with IamApi also `attached()` (api) |
| function / stream `runs_as` role | 4 | already from LambdaApi and FirehoseApi (api) |
| event `acted_as` / `signed_in_via` / `acted_on` | 5 | already from Activity (content) |

**Same edge, two sources.** When IamApi gives a `has_policy` edge that the stack already gave, `Graph` keeps **one** edge per `from`, `rel`, `to`, with the strongest evidence (`api` over `template`, the schema's order) and both sources listed in `source`. ontology.aws.a's builder applies the same rule, so the golden stays comparable when the twin starts answering `ListAttachedRolePolicies`.

## Step 2 (later, iam.aws.a)

`iam:GenerateServiceLastAccessedDetails` and `iam:GetServiceLastAccessedDetails` per role: which services a role actually used, the real over-privilege signal. Generate starts a job but IAM classes it as a read. Its own short design when step 1 is in.

## Order

1. Twin patch (aws.c lands; dev.2.aws.a writes it with tests, as cloudformation.aws.a did for CloudFormation).
2. `iam-api.js`, `iam.openapi.json`, tests over the twin and over a recording `send`.
3. `Graph.add.iam` and the one-edge-strongest-evidence rule; golden slice grows by the IAM edges.

## Security notes

- Trust policies and policy documents can name external accounts, organisations and GitHub repositories: shown as data (textContent), kept in the page only.
- The read role gains IAM reads in template v3 only after iam.aws.a and security.aws.a agree the list; `iam:GetPolicyVersion` on customer policies shows their full text, which is the point, and is still read only.
- R-010 applies to `site/api/**` as for every piece of design 03.
