# Note 02: can the page call Lambda, Firehose and CloudWatch from the browser?

lambda.aws.a@SovereignWebsite.dinis, 23 Nov 2026 ~10:30 UTC. Closes the open question in the first note and design 01, section 9. Answered from AWS documentation only; nothing was sent to AWS.

## Answer

Yes, for all three, on the same footing as the services the page already calls (STS, IAM, CloudFormation, Cost Explorer, S3).

AWS's service table for the SDK for JavaScript v2 ([SERVICES.md](https://github.com/aws/aws-sdk-js/blob/master/SERVICES.md), read 23 Nov 2026 ~10:25 UTC) has an "Allows CORS" column. These rows are marked as allowing it, with the same API versions the twin speaks:

| Service | API version | Allows CORS | Twin calls |
|---|---|---|---|
| AWS Lambda | 2015-03-31 | yes | ListFunctions, GetFunctionConfiguration |
| Amazon Kinesis Firehose | 2015-08-04 | yes | ListDeliveryStreams, DescribeDeliveryStream |
| Amazon CloudWatch | 2010-08-01 | yes | GetMetricData |
| Amazon CloudWatch Logs | 2014-03-28 | yes | (none yet; a later "recent invocations" view) |

For comparison, the services the page already reaches from the browser are marked the same way in that table: STS, IAM, CloudFormation, Cost Explorer, S3.

## Limits of this answer

- The table belongs to the v2 SDK, which AWS has ended support for; I found no equivalent table for v3. It says what AWS documented about the service endpoints, which do not change with the SDK version, but it is documentation, not a test.
- The first real check is the owner's own browser in real-AWS mode, with the read role, once the permissions below exist. If a call fails there with a CORS error, the page must say so in plain words (design 01, section 2) and nothing else breaks.
- CORS only lets the browser read the answer. Every call still needs the read role's permission and a SigV4 signature, as today.

## What follows

- **Read permissions** (first note), for iam.aws.c / iam.aws.a and security to weigh, unchanged: `lambda:ListFunctions`, `lambda:GetFunctionConfiguration`, `firehose:ListDeliveryStreams`, `firehose:DescribeDeliveryStream`, `cloudwatch:GetMetricData`. No `lambda:GetFunction`. Adding them is an AWS change: a plan for aws.c to prepare and Dinis to approve.
- **connect-src**: today `https://*.amazonaws.com` already covers `lambda.<region>`, `firehose.<region>` and `monitoring.<region>.amazonaws.com`. If it is ever narrowed (security's R-013 c), these three hosts join the list.
- **No other route needed**: no proxy, no server code, which the site forbids anyway.
